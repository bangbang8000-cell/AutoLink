> 本文档与《PRD_V2.4》分离，专注于工程实施层面：阶段划分、任务清单、测试策略、风险管理、交付里程碑。

> 前置条件：PRD_V2.4 评审通过并获用户授权后方可启动开发。

## 一、总体策略

### 1.1 核心原则

1. **分阶段交付**：每阶段产出可运行版本，避免大爆炸式集成
2. **数据先行**：设备库/光模块库/规则库等数据资产优先于 UI 开发
3. **后端先行**：Python 引擎能力扩展优先于前端对接
4. **测试同步**：每个阶段完成后立即补充测试，不积累技术债
5. **P0 优先**：2.4.0 版本聚焦 P0 功能，P1 功能可顺延至 2.4.1/2.4.2
6. **向后兼容**：V2.3 项目自动迁移，用户无感知升级

### 1.2 阶段总览

| 阶段 | 主题 | 优先级 | 工作量 | 交付物 |
|------|------|--------|--------|--------|

**Rail 算法核心逻辑**：

```python
class RailTopology:
    """Rail-Optimized 拓扑（NVIDIA SuperPOD 参考）
    
    设计原则：
    - 每 GPU 服务器 8 张 NIC，每张 NIC 连一个 Rail
    - 每 Rail 独立 leaf 交换机（8 个 Rail = 8 组 leaf）
    - Rail leaf 之间通过 spine 互联
    - 同一服务器内的 8 张 NIC 分别连到 8 个不同 Rail
    """
    def __init__(self, num_servers, rail_count=8, switch_ports=64, ...):
        self.rail_count = rail_count
        # 每 Rail 的 leaf 数 = ceil(num_servers / (switch_ports/2))
        # 每 Rail 的 spine 数 = leaf 数
```

**布局算法核心**：

```typescript
// 三维布局：先分层（Y），再分区（X 域），再分组（区内 Pod/Rail）
function computeLayoutV2(
  nodes: TopologyNode[],
  edges: Edge[],
  config: LayoutConfig
): NodePosition[] {
  // 1. 按网络域分组节点
  const domainGroups = groupByNetworkDomain(nodes)
  // 2. 为每个域分配 X 范围（域间留 domainGap）
  const domainRanges = allocateDomainRanges(domainGroups, config)
  // 3. 域内按 Pod/Rail 聚簇
  for (const domain of domainGroups) {
    const podGroups = groupByPod(domain.nodes)
    // 4. 每簇内自适应间距排列
    for (const pod of podGroups) {
      layoutPodGroup(pod, config)
    }
  }
  // 5. 按层（Core/Spine/Leaf/Server）固定 Y 坐标
  assignLayerY(positions, config.layerY)
}
```

## 十一、测试策略

### 11.1 测试金字塔

```
            ▲
           / \
          / E2E \          ← Playwright（20 用例）
         /-------\
        / 集成测试 \        ← 前后端联调（50 用例）
       /-----------\
      /  单元测试    \      ← Vitest + pytest（290 用例）
     /---------------\
```

### 11.2 测试分工

| 层级 | 工具 | 责任 | 运行时机 |
|------|------|------|---------|
| 后端单元 | pytest | 每个 Python 模块独立测试 | `npm run test:backend` |
| 前端单元 | Vitest | Store/工具函数测试 | `npm run test` |
| 前端组件 | Vitest + RTL | 组件渲染测试 | `npm run test` |
| 集成测试 | Vitest + pytest | IPC mock + 前后端联调 | `npm run test:all` |
| E2E | Playwright | 跨进程核心链路 | CI only |
| 性能基准 | pytest-benchmark + Vitest | 大规模性能回归 | CI only |

### 11.3 CI 集成

```yaml
# .github/workflows/ci.yml 新增
jobs:
  e2e:
    runs-on: windows-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npx playwright install
      - run: npm run test:e2e

  performance:
    runs-on: ubuntu-latest
    steps:
      - run: npm run test:perf
      - run: python -m pytest tests/perf/ --benchmark-compare
```

### 11.4 测试用例命名规范

- 后端：`test_{模块}_{场景}.py`，如 `test_rail_topology_8_rail_grouping.py`

- 非发布 commit 包含 `[skip ci]`（用户偏好）

### 14.2 代码规范

- TypeScript：`strict: true`，`import type` 分离（V2.3 教训）
- Python：类型注解 + docstring，async/await 风格（无回调）
- ESLint + Prettier 强制
- Python 设备 JSON 必须通过 schema 校验

### 14.3 IPC 通道命名

- 遵循 `[feature]:[action]` 规范（如 `design:recommend`、`export:cabling`）
- 新增通道必须在 `electron.d.ts` + `preload.ts` + `handlers.ts` 三端同步

### 14.4 设备库 JSON 规范

- 文件名：`{vendor}_{model}.json`（小写 + 下划线）
- 必填字段：id/vendor/model/category/u_height/power_watts/ports
- V2.4 新增字段为可选，保证向后兼容
- 所有 JSON 必须通过 `schema_validator.py` 校验
