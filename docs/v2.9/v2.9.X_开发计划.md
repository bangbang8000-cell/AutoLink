## 二、v2.9.0 — 机柜核心算法

### 任务清单

| ID | 任务 | 文件 | 验收 |
|----|------|------|------|
| T1 | 新建 `rack_allocation.py`：`DeviceSlot` 数据类（obj_type/group/power/u_height）+ `RackAllocator` 类，实现 `allocate(devices, rack_type, power_limit, gpu_dedicated)` 多约束装箱纯函数。规则：①功率>50%上限的 GPU 独占机柜；②GPU 功率装箱；③通算/存储功率+U位装箱；④交换机按网段聚柜（网络柜）；⑤每柜功率 ≤ 上限且 U 位 ≤ rack_type | `backend/rack_allocation.py`（新建） | 4 类设备 3 组正反例通过 |
| T2 | `NetworkDesignerV2.create_network_objects` 改造：GPU/存储/通算服务器收集为 `DeviceSlot` 列表 → 调用 `RackAllocator` → 回填 `cabinet_id/cabinet_name/start_u/end_u`；`_assign_cabinet` 删除（或降级为兼容函数） | `backend/designer.py` | 128×H100 → 128 柜；U 位按 u_height 连续无冲突 |
| T3 | 交换机机柜分配：param/storage/oob/biz 交换机全部收集进 `RackAllocator`，网络柜类型标记，回填 cabinet/U 位 | `backend/designer.py`（交换机创建处）/ `backend/topology.py`（FatTree/AccessAgg 创建后统一分配） | 所有交换机 cabinet_id 非空，拓扑连线机柜字段有值 |
| T4 | `_calculate_power_summary` 重构：遍历 servers + 全部交换机，输出每柜 `type/deviceCount/totalPower/percent/exceeded/devices`；机柜类型从分配结果继承 | `backend/engine.py` | 交换机功率计入机柜，报告数值与分配一致 |
| T5 | V002 升级：机柜功率阈值 = `min(散热上限, power_limit_per_rack)`，功率统计含交换机；校验上下文 cabinets 含交换机 | `backend/validation.py` | 6000W 柜塞 10.2KW×2 GPU 触发 ERROR |
| T6 | `estimate_cabinet_power_density` 联动：`num_cabinets` 含网络柜（从 designer 全部设备 cabinet 集合计算） | `backend/estimation.py` / `backend/engine.py` L120 | 密度估算与分配一致 |
| T7 | 单元测试 `test_rack_allocation.py`：H100 独占、H200 独占、Atlas 16KW→2台、MLU590 12KW→3台、通算 15 台/柜、交换机 U 位约束、gpu_dedicated 开/关、U 位无冲突、边界（功率恰好=上限） | `tests/backend/test_rack_allocation.py`（新建） | pytest 全绿 |

### 验证
- `python -m pytest tests/backend/test_rack_allocation.py -v` 全绿
- `python -m pytest tests/backend/ -v` 全量回归（既有用例不回归）

## 八、风险提示

- 分配算法变更会改变既有项目机柜编号：前端优先采用已保存 `rack_layout.json`（v2.9.2-T3），后端新分配仅作用于重新渲染
- 交换机聚柜改变机柜总数：报告/密度/校验同步联动（v2.9.0-T4/T5/T6），避免数字打架
