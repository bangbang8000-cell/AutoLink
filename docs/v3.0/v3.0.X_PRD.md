## 一、系列愿景与定位

### 1.1 问题背景

v2.9.9 已达成"专业、完整、可靠"的单机工具目标。3.X 需回应四个演进：

- **组网需求演进**：双平面（8 网卡 × 双口）、ZCube、华为超节点、B300 800G IB、GPU 异构（P/D 集群独立组网）、三合一网卡等成为主流诉求，现有四网硬编码模型无法承载；
- **使用方式演进**：用户希望"用自然语言描述需求 → 工具直接生成方案"，且**一切能力先有 CLI**（可脚本化、可测试、可被 AI 调用），再谈 UI 与智能化；
- **规划粒度演进**：机房不是"画一张图"，而是"矩阵 + 占位 + 类型 + 约束 → 智能落位"的可视化规划闭环；
- **协作方式演进**：项目/模板需要分享与同步，但登录/云端**最后实现**——本地功能与本地 AI 优先。

### 1.2 产品定位

> **"说出你的组网需求，AutoLink 替你生成方案"** —— 3.X 是 AI 智算中心网络规划的智能工作平台：显式 CLI 能力层 + AIHUB 对话 + 新组网引擎 + 机房智能落位，登录与云端协作收尾。

### 1.3 系列目标（六更）

| 维度 | 目标 | 关键举措 | 落地系列 |
|------|------|----------|----------|
| **更智能** | 对话式生成与管理；AI 经 CLI 统一调用 | CLI 能力层 + AIHUB + 容量规划内核 + ATOP | 3.1/3.2 |
| **更高效** | 新组网即插即用；CLI 脚本化 | 拓扑插件化 + 正交 GPU 池 + CLI 全覆盖 | 3.0/3.1 |
| **更好用** | 机房可视化落位；双轨制交互 | 机房矩阵 + 智能落位 + AI 生成/人工确认 | 3.0/3.1 |
| **更美观** | 品牌主题 + 新组网视觉 + 机房视觉语言 | 主题 token、3D/机房/报告升级 | 3.2 |

## 三、3.X 总体架构目标

```
┌─────────────────────────────────────────────────────────────┐
│ 渲染层（React，保持 0 网络红线）                               │
│  UI: 向导 / 工作区 Tab / AIHUB 面板 / 机房矩阵 / 云空间         │
│  Store: project/design/device-library/ai/auth/cloud/room      │
├─────────────────────────────────────────────────────────────┤
│ 主进程（Electron，网络与凭据唯一出口）                          │
│  IPC 域: project/template/design/device-library/render/room   │
│          + ai:* / auth:* / cloud:*                            │
│  服务: python-agent.service（持久进程/NDJSON/CLI 统一调用）     │
│        auth.service（OAuth+safeStorage，3.3）/ cloud.service  │
├─────────────────────────────────────────────────────────────┤
│ 能力层：显式 CLI（AI 与 UI 的统一入口）★ 3.X 架构红线           │
│  autolink-cli: project/template/device/design/render/config/  │
│                capacity/room 子命令，JSON/NDJSON 输出          │
├─────────────────────────────────────────────────────────────┤
│ Python 引擎（PyInstaller 打包分发）                            │
│  engine: @register_action（CLI 底层执行）                      │
│  topology: 插件化（dual_plane/zcube/huawei_supernode/         │
│            combined_eth/scale_up/fat_tree/rail）              │
│            × 正交 GPU 池（P/D 集群独立选组网方案）              │
│  capacity / room / validation / exporter / config             │
└─────────────────────────────────────────────────────────────┘
```

**五条架构红线**：
1. 渲染层保持 0 网络请求、0 Node 权限。
2. 凭据只入 `safeStorage`，永不明文落盘。
3. 一切能力走 `ProjectConfig` 单一事实源 + schema 版本迁移链，兼容 2.9.9 全部旧模板/项目。
4. **一切能力先有 CLI**：新功能必须先实现 CLI 命令（可脚本化/可测试/可审计），AI Agent 通过 CLI 调用，UI 与 AI 共享同一能力层。
5. 拓扑插件化 + 正交模型：组网形态（横向）与 GPU 池/集群（纵向）正交，P/D 集群可独立选择组网方案。

## 四、核心能力规划

### 4.1 能力一：拓扑引擎 3.0（新组网支持）

**目标**：双平面 16 Leaf、ZCube、华为超节点、B300 800G IB、三合一网卡、正交异构（P/D 集群独立组网），新增组网"即插即用"。

#### 4.1.1 双平面 16 Leaf 组网（合并为一个能力）

| 项 | 说明 |
|----|------|
| 定义 | **双平面与 16 Leaf 是同一能力**：服务器配 8 张参数网卡、每卡 2 口（dual-port），接口 1 连平面 A、接口 2 连平面 B；每平面独立 Leaf 层（**每平面 8 Leaf，双平面共 16 Leaf**）。典型组合：**CX7 2×200G 组 H100/H200 双平面、CX8 2×400G 组 B300 双平面** |
| 与 Rail 模式区别 | Rail（现有 `rail_topology`）：每网卡单口、N 网卡 → N Rail（1:1）；双平面：每网卡双口分属 2 平面，每服务器每平面承载"网卡数"个口（8 口/平面） |
| 关键需求 | `topology.param_planes` 可选段：每平面 {leaf_count（8）、protocol、speed、switch_ports、uplink} + `param_nics_per_server=8` + `ports_per_nic=2`；端口容量显式化（每服务器每平面 8 口 → Leaf 下联推导）；双平面配置/校验/导出/机柜/拓扑可视化按平面展开；Leaf 数量与收敛比联动校验（V016 扩展） |
| 验收场景 | 1024×B300：8×CX8（2×400G）→ 16 口/服务器，双平面各 8 Leaf、800G IB |

#### 4.1.2 ZCube 组网（论文定义：扁平化二部图）

| 项 | 说明 |
|----|------|
| 定义 | 依据《From ATOP to ZCube: Automated Topology Optimization Pipeline and A Highly Cost-Effective Network Topology for Large Model Training》（清华 SIGCOMM 2025，智谱已落地）：**完全扁平化二部图互联**——取消 Spine 层、两组 Leaf 直连 GPU、任意 GPU 间独享最短路径、双端口网卡单轨/多轨混合接入、模型通信模式驱动路由。实测：推理吞吐 +15%、硬件成本 -33%、TTFT -40.6% |
| 与华为超节点区别 | **ZCube**：扁平二部图 + 无 Spine + 双口混合接入 + 模型流量驱动 + 大规模线性扩展；**华为超节点**（见 4.1.3）：UB 域内全对等 + 域间 Scale-Out + 固定规模（昇腾专属）——两者是不同组网 |
| 关键需求 | 新建 `zcube_topology.py`：GPU-两组 Leaf 二部图 + 无 Spine + 双口单轨/多轨混合接入 + 最优路径布线；`ZcubeNetworkPlugin` 接线；校验新增 ZCube 专属规则（无 Spine 层级一致性、双口接入比例、路径唯一性）；ATOP 自动优化流水线并入 3.2 |
| 验收场景 | 1024 GPU ZCube：双口混合接入、无 Spine、可渲染可导出可校验 |

#### 4.1.3 华为超节点组网（UB 全对等）

| 项 | 说明 |
|----|------|
| 定义 | 华为昇腾超节点（CloudMatrix 384 等）：固定规模 NPU 以 **UB（UltraBus）光纤域内全对等直连**（如 384 NPU），域间经 800G 交换机 Scale-Out。与 ZCube 是**两种不同组网** |
| 关键需求 | 接入现有 `ub_topology.py`（UB 全对等算法已完备）转生产 + `HuaweiSuperNodePlugin` 接线 + 域间 Scale-Out 上联算法；昇腾 800G 交换机档案 |
| 验收场景 | 384 NPU CloudMatrix 超节点：域内 UB 全对等 + 域间 800G Scale-Out，可渲染可导出 |

#### 4.1.4 B300 800G IB

| 项 | 说明 |
|----|------|
| 现状 | 设备库已具备 `nvidia_q3200_72_800g_ib`（72×800G）/`nvidia_q3400_144_800g_ib`（144×800G），自动选型已映射 |
| 关键需求 | 接线验证 800G IB 2/3-tier 公式（`calc_max_2tier(72,p)`）；GB300 NVL72/PD 形态机架档案（liquid/高功率柜/Scale-Up NVLink 72 域）+ CX7/CX8 双口网卡档案（2×200G/2×400G）；B300 双平面默认 CX8 2×400G（见 4.1.1） |
| 验收场景 | GB300 NVL72×4（288 GPU）+ 1024×B300 双平面 800G IB 可生成 |

#### 4.1.5 三合一网卡场景（带内管理 + 业务 + 存储）

| 项 | 说明 |
|----|------|
| 定义 | 服务器主网卡同时承载**带内管理（in-band management）+ 业务 + 存储**流量（VLAN/优先级区分）。**OOB 带外网络独立保留，不参与合并**。**带内管理 + 业务 2 合一**是绝大多数场景的默认形态，3 合一只需在 2 合一基础上并入存储。常见于超节点（GB300 NVL72）与小规模项目 |
| 关键需求 | `networks` 段新增合并开关（`eth_combined: true`）：storage+biz+带内管理合并为单一"融合以太网"网络域（一台交换机层级），OOB 保持独立；`interface_models` 多角色标注（`roles: ['storage','biz','inband_mgmt']`，不含 oob）；校验适配（V005 融合网速率、带内管理可达性、V009 存储冗余对融合网生效、V008 OOB 规则保持不变）；导出按角色过滤；选型联动（融合交换机档案） |
| 验收场景 | GB300 NVL72：参数网 800G IB + 融合网 25G/100G（三合一）+ 独立 OOB 1G，可渲染可导出可校验 |

#### 4.1.6 正交异构组网（GPU 异构 × 组网形态正交，PD 分离）

| 项 | 说明 |
|----|------|
| 定义 | **GPU 异构（PD 分离）与组网形态是正交的两个维度**：P 集群（参数/计算）与 D 集群（数据/存储）**各自独立选择组网方案**（双平面/ZCube/华为超节点/FatTree/Rail…），每集群含自己的 GPU 池、规模、协议与收敛配置。PD 分离 = 计算面与数据面在平面、端口上分离的设计模式（含 GB300 PD 机架形态） |
| 关键需求 | 数据模型：`clusters: [{cluster_id, role: 'P'|'D', network_mode, gpu_pools: [{pool_id, profile_ref, count, nic_config, rack_pref}], scale}]`；**模板设计**支持多集群方案组合（P 集群选 A 组网、D 集群选 B 组网）；designer 多集群并行设计 + 合并拓扑；校验/机柜/导出按集群；异构功率/散热校验（V002/V012 按池） |
| 验收场景 | P 集群：64×H100 双平面 16 Leaf；D 集群：32×B300 FatTree + 三合一网卡——同项目混合，独立组网、独立收敛 |

### 4.2 能力二：CLI 显式能力层 ★ 3.X 架构红线

**目标**：一切能力先有 CLI。CLI 是 AI Agent、脚本、CI 与 UI 的统一入口。

| 项 | 说明 |
|----|------|
| 定位 | `backend/cli.py`（autolink-cli）：每个 engine action 有对应子命令，JSON 输出（流式命令 NDJSON），`--help` 完备；无 GUI 依赖，可脚本化/可测试/可审计 |
| 命令域 | project（list/create/duplicate/rename/delete/export/import）、template（list/create/update/preview/health/export/import）、device（list/get/save/delete/import/export）、design（generate/validate/estimate/report）、render（export/status）、config（get/set/validate/list-schema）、capacity（recommend）、room（matrix/get/set-occupy/set-type/place/optimize）、ai（chat/stream） |
| 与引擎关系 | CLI = action 注册表的显式化封装：`@register_action` 的 handler 自动获得 CLI 子命令；新增能力 = 新增 action = 自动有 CLI |
| AI 调用 | AI Agent 的工具（tool）白名单 = CLI 命令白名单；调用轨迹 = CLI 命令日志（天然审计）；持久进程内直接调用命令函数（免 subprocess 开销） |
| UI 调用 | 主进程 IPC handler 内部统一改走 CLI 命令函数，UI 与 AI 行为完全一致 |
| 收益 | 新功能先 CLI 后 UI（UI 是 CLI 的可视化壳）；CLI 集成测试成为 CI 门禁；AI 输出永远可复现可校验 |
| 验收场景 | `autolink-cli design generate --config xxx.json --stream` 输出与 GUI 完全一致；AI 执行"渲染当前项目"= 调用 `autolink-cli render export`，轨迹可查 |

### 4.3 能力三：AIHUB（对话式智能管理，AI 经 CLI 调用）

**目标**：用户用自然语言管理设备库、模板、项目，触发渲染，并根据组网需求或示例文件生成项目/模板；**所有执行动作经 CLI 完成**。

#### 4.3.2 双轨制交互模式

- **轨道 A（AI 直接执行）**：查询/渲染/导出等低风险操作直接执行。
- **轨道 B（AI 生成 + 人工确认）**：创建/修改项目、模板、设计配置等高风险操作，AI 预填向导/表单由用户确认后落盘。
- 所有执行动作留"工具调用轨迹"卡片（CLI 命令 + 参数 + 结果摘要 + 可回滚）。

#### 4.3.3 AIHUB 技术形态

| 项 | 说明 |
|----|------|
| 实现策略 | **整体移植 MagicCommander `ai_hub/`**（参考代码 `D:\MyCoding\_reference\MagicCommander\ai_hub\`）：独立 FastAPI 子进程（端口 autolink 专用，`AI_HUB_READY` 就绪握手）+ Agent 循环（plan→act→validate→recover→report，SSE 流式，max 5 轮）+ 组合式提示词 + 三层记忆 + Skills 引擎；领域内容（工具/prompt/技能/记忆 schema）按 AutoLink 重写 |
| 工具（Tool） | **= autolink-cli 命令白名单**（见 4.2），沿用 MagicCommander `_run_python_cli()` 模式并加固：命令模板化（只允许 schema 声明字段映射固定命令位，禁止自由拼接 argv）+ 输出过滤（只取 status 结果行，防污染 LLM 上下文）+ 权限分级（TOOL_PERMISSIONS：auto/notify/confirm） |

| LLM 接入 | 复用 `llm/provider.py`：9 厂商 OpenAI 兼容单类适配 + BYO-Key（secrets 文件 chmod 600 + 热重载）+ 连接测试 + 模型列表 + 关键词策略路由 |
| 对话通道 | 复用 `ai_hub/api/chat.py` SSE 端点 + `aiHub.service.ts` 流式解析；前端沿用 `chat.store`/`ChatPanel`/`PlanDisplay`（📋 执行计划可视化） |
| 会话/记忆 | 复用 `memory/engine.py`（user_profile/habits/project_history JSON 三层记忆）+ 前端会话持久化 |
| 安全 | CLI 命令白名单 + 权限分级 + 轨道 B + 命令审计日志 + 无外部网络降级模式（BYO-Key 本地） |

### 4.4 能力四：容量规划智能内核

作为 AIHUB"需求生成项目"的计算内核，以 `autolink-cli capacity recommend` 暴露。内容：`model_parser`（模型档案解析）/ `comm_calculator`（AllReduce/All-to-All/P2P 通信量）/ `topology_recommender`（带宽→Scale-Up/Scale-Out/收敛比/层数推荐）/ `rules`（参数化经验规则）/ `presets`（预置模型档案 10+ 个）。落地节奏：3.1.3（R7.4）基础版，3.2.0（R9.1）增强版。

### 4.5 能力五：机房矩阵可视化与智能落位 ★ 新增

**目标**：从"机房平面图 PoC"升级为"矩阵 + 占位 + 类型 + 约束 → 智能落位"的可视化规划闭环。

| 项 | 说明 |
